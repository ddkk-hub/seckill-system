# 阶段二设计与实施状态

状态：设计及环境准备中，尚未完成阶段二。

## 1. 目标
实时库存放入 Redis，例如 product_stock_1；Lua 原子检查并预扣。保留同步 MySQL 下单、订单查询，不引入 MQ。将库存竞争从 MySQL 热点行迁移到 Redis，售罄请求无需访问 MySQL。

## 2. 设计原因
Redis Lua 执行期间不会被其他命令插入，能够将判断与扣减组成原子操作。但脚本原子执行不意味着 Redis 与 MySQL 是同一个事务，也不意味着脚本运行错误时自动撤销之前的写入。必须在修改前检查数据类型及参数。

MySQL product.stock 在 Redis 模式中是导入基线，不再每单更新；实时库存读 Redis。保存基线时记录历史订单数量，阶段一的已有订单不能再次扣除。停止旧版下单后再导入库存，不允许两种库存模式同时售卖同一个商品。

初始化为显式离线操作，不能每次应用重启覆盖 Redis。缺失库存、连接失败时拒绝下单，不能自动从旧 MySQL 库存补满。Redis 成为库存数据源后，需要持久化、noeviction 和停单对账；不能把它当作可随意清空的缓存。

预扣成功后同步写订单。确认数据库回滚后执行一次库存补偿；提交结果未知、Redis 响应超时或进程崩溃时保留预扣并记录异常，避免误补造成超卖。完整跨系统故障恢复仍是本阶段限制，不能宣称具有分布式事务保证。

## 5. 测试与压测计划
功能：初始化、查询、购买、售罄、非法参数。
正确性：并发不超卖，重复初始化不能补满库存，明确回滚时只补一次，Redis key 缺失不自动补库存，Redis 不可用时无新订单。
一致性：导入库存 = Redis 剩余库存 + 本阶段成功订单数量（无在途/故障预扣时）；存在故障预扣时需把在途/待对账数量纳入等式。
性能：与阶段一使用相同请求模型和连接池，分别记录成功下单 QPS 与售罄拒绝吞吐；记录平均/最大响应、成功/拒绝/失败、数据库锁等待和 CPU。先复现 1、10、100 并发初始基线，可靠容量结论需加长到至少 60 秒并多轮重复。

## 6. 与阶段一比较
新增 Redis 和 Lua，减少库存查询及扣减对 MySQL 的访问。订单仍同步写库，所以成功下单吞吐仍受数据库写入限制，不承诺固定倍数提升。第一阶段已经避免超卖，第二阶段优化的是竞争位置和数据库压力。
